# Minio 上传性能调优指南

## 概述

本文档记录了 plugin-record 在不同网络环境下向 Minio 上传录像文件的性能分析与配置建议。基于实际场景（72 个 250MB 文件 / 每台服务器）进行估算。

## 上传机制

### 核心流程

```
录像完成 → 获取并发信号量 → 带超时上传 → 失败则指数退避重试 → 重试耗尽写异常记录
```

### 可配置参数

| 参数 | 说明 | 默认值 |
|---|---|---|
| `maxconcurrentuploads` | 单节点最大并发上传数 | 4 |
| `uploadtimeout` | 单次上传超时时间 | 30m |
| `maxretries` | 上传失败最大重试次数 | 3 |
| `retryinterval` | 重试基础间隔（指数退避） | 10s |

### 指数退避策略

重试间隔 = `retryinterval × 2^(attempt-1)`

示例（`retryinterval: 10s`）：第1次 10s → 第2次 20s → 第3次 40s

示例（`retryinterval: 30s`）：第1次 30s → 第2次 60s → 第3次 120s → 第4次 240s → 第5次 480s

## 场景分析

### 测试基准

- 每台服务器：72 个文件 × 250 MB = 18 GB
- 千兆网络实际可用带宽：~90 MB/s（理论 125 MB/s，扣除 TCP/HTTP 协议开销约 72%）

### 场景一：单台服务器 → 千兆 Minio 单节点

| 指标 | 数值 |
|---|---|
| 聚合上传速率 | ~90 MB/s（~720 Mbps） |
| 单连接速率（8并发） | ~11 MB/s |
| 单文件耗时 | ~22 秒 |
| 批次数 | 72 ÷ 8 = 9 批 |
| 总耗时 | **~3.3 分钟** |

---

### 场景二：15 台服务器 → 千兆 Minio 单节点

Minio 端 1 Gbps 入口成为瓶颈。

| 指标 | 数值 |
|---|---|
| 总数据量 | 270 GB |
| 总并发连接数 | 15 × 8 = 120 |
| Minio 有效吞吐 | ~90 MB/s |
| 每台分得带宽 | ~6 MB/s |
| 单文件耗时 | ~5.5 分钟 |
| 全部完成 | **~51 分钟** |

---

### 场景三：15 台服务器 → 3 Gbps Minio 4节点集群（EC:2+2）

#### Minio 4节点 Erasure Coding 写入特性

4 节点默认 EC:2+2（2 数据分片 + 2 校验分片），**数据膨胀系数 = 2x**。

```
集群接入带宽：           3 Gbps = 375 MB/s
协议开销后（~80%）：      ~300 MB/s
纠删码膨胀后有效吞吐：     300 ÷ 2 = ~150 MB/s
节点间同步开销后（~10%）：  ~135 MB/s
```

#### 8 并发 / 每台（当前默认）

| 指标 | 数值 |
|---|---|
| 总并发连接数 | 15 × 8 = **120 个** |
| 每 Minio 节点连接数 | 120 ÷ 4 = **30 个** |
| 集群有效吞吐 | **~135 MB/s** |
| 每连接分得带宽 | 135 ÷ 120 ≈ **1.1 MB/s** |
| 每台聚合带宽 | 1.1 × 8 ≈ **9 MB/s** |
| 单文件耗时 | 250 ÷ 1.1 ≈ **3.8 分钟** |
| 每台总耗时（9批次） | 9 × 227s ≈ **34 分钟** |
| 全局总耗时 | 270 GB ÷ 135 MB/s ≈ **33 分钟** |

#### 2 并发 / 每台（优化方案）

| 指标 | 数值 |
|---|---|
| 总并发连接数 | 15 × 2 = **30 个** |
| 每 Minio 节点连接数 | 30 ÷ 4 = **7-8 个** |
| 集群有效吞吐 | **~135 MB/s**（不变，瓶颈在 Minio） |
| 每连接分得带宽 | 135 ÷ 30 ≈ **4.5 MB/s** |
| 单文件耗时 | 250 ÷ 4.5 ≈ **56 秒** |
| 每台总耗时（36批次） | 36 × 56s ≈ **34 分钟** |
| 全局总耗时 | **~33 分钟（不变）** |

#### 8 并发 vs 2 并发对比

| 指标 | 8 并发 | 2 并发 |
|---|---|---|
| 总连接数 | 120 | 30 |
| 每连接带宽 | 1.1 MB/s | 4.5 MB/s |
| 单文件耗时 | ~3.8 分钟 | ~56 秒 |
| **全局总耗时** | **~33 分钟** | **~33 分钟** |
| TCP 效率 | 低（连接过细） | 高（每连接更饱满） |
| 超时概率 | **高** | **低** |
| Minio 节点压力 | **高**（30连接/节点） | **低**（7-8连接/节点） |
| 重试风暴风险 | **严重** | **可控** |

**结论**：总耗时相同（瓶颈在 Minio 的 135 MB/s），但高并发只带来更高的故障概率和资源开销，没有吞吐收益。

### 场景汇总

| 场景 | Minio 带宽 | 有效吞吐 | 15台总耗时 |
|---|---|---|---|
| 千兆单节点 | 1 Gbps | ~90 MB/s | ~51 分钟 |
| **3G 4节点 EC:2+2** | **3 Gbps** | **~135 MB/s** | **~33 分钟** |
| 万兆单节点 | 10 Gbps | ~900 MB/s | ~5 分钟 |
| ≥ 15 Gbps | ≥15 Gbps | ~1350 MB/s | ~3.3 分钟 |

## 120 并发下的隐患分析

### TCP 连接争抢

每连接 1.1 MB/s 远低于 TCP 窗口高效利用阈值，大量低速连接导致：
- TCP 拥塞窗口频繁调整
- 实际吞吐可能跌至 100-120 MB/s
- 总耗时可能升至 37-45 分钟

### Minio 节点资源消耗（每节点 30 并发）

| 资源 | 负载 | 风险 |
|---|---|---|
| 并发连接 | 30 个 | goroutine/内存开销尚可 |
| 文件描述符 | 30 × EC分片 ≈ 120 fd | 需确认 ulimit 设置 |
| 磁盘 IOPS | 30 路并发写 | **HDD 集群会严重退化** |
| 内存 | 30 × 上传缓冲区(~16MB) ≈ 480 MB | 中等压力 |

### 超时与重试风暴

120 连接竞争带宽，部分连接可能因超时同时触发重试，导致瞬间连接数翻倍，形成雪崩效应。

## 推荐配置

### 3G 4节点集群 / 15 台服务器（推荐）

```yaml
record:
  storage:
    endpoint: minio-cluster.example.com
    accesskey: xxx
    secretkey: xxx
    bucket: recording-bucket
    maxconcurrentuploads: 2    # 15台×2=30总并发，对集群友好
    uploadtimeout: 20m         # 单文件最坏约 4 分钟，留足余量
    maxretries: 5              # 拥挤环境易出错，多给重试
    retryinterval: 30s         # 退避序列：30s→60s→120s→240s→480s
```

### 3G 4节点集群 / 15 台服务器（坚持 8 并发）

```yaml
record:
  storage:
    endpoint: minio-cluster.example.com
    accesskey: xxx
    secretkey: xxx
    bucket: recording-bucket
    maxconcurrentuploads: 8    # 总并发 120，压力较大
    uploadtimeout: 15m         # 单文件最坏 8 分钟
    maxretries: 5              # 120 连接争抢容易出错
    retryinterval: 30s         # 大退避间隔，避免重试雪崩
```

### 千兆 Minio 单节点 / 少量服务器

```yaml
record:
  storage:
    maxconcurrentuploads: 4
    uploadtimeout: 15m
    maxretries: 5
    retryinterval: 15s
```

### 万兆 Minio / 带宽充足

```yaml
record:
  storage:
    maxconcurrentuploads: 8    # 带宽充足，可打满
    uploadtimeout: 5m          # 单文件很快完成
    maxretries: 3
    retryinterval: 10s
```

## 调优原则

1. **总耗时由 Minio 端吞吐决定**，提高单节点并发数不会加速总上传，只会增加故障率
2. **降低并发、提高单连接带宽**是更优策略，单文件快进快出，减少超时和重试
3. **指数退避间隔**在高并发场景下应设置更大（≥30s），防止重试风暴
4. **磁盘类型关键**：HDD 集群下高并发写会导致 IOPS 瓶颈，实际吞吐可能远低于网络带宽
5. **监控指标**：关注 Minio 的 `s3_requests_errors_total`、节点 CPU/IO wait、上传异常记录表
